# Architecture

How Ever RSVP is put together, and why it is put together that way.

Companion documents:
- [LAYOUT-SPEC.md](LAYOUT-SPEC.md) — the frozen v4 contract every layout module implements
- [DEPLOY.md](DEPLOY.md) — going live

---

## 1. The shape of the thing

**The product is `public/`: plain HTML, CSS and vanilla JavaScript.** No
framework, no bundler, no transpile step, no database, no server.

That is a deliberate constraint, not an accident of history. It buys:

- **Deployability** — the deliverable is a folder. Any static host serves it.
- **Longevity** — nothing to upgrade, nothing that rots when a major version lands.
- **Privacy by construction** — with no server there is no place to store customer
  data, so there is none to leak. Everything lives in the customer's browser.

The cost is equally real and worth stating: no accounts, no cross-device sync,
no server-side RSVP aggregation. An event lives in one browser on one device.
The product's copy, its privacy policy and its terms all say so plainly.

Next.js appears in `package.json` for exactly one reason: `next dev` is a
convenient local static server that also applies the production response
headers, so development matches production. **No React code exists in the
product.** `src/app/` is two files that keep the App Router valid.

## 3. The JavaScript modules

Every file in `public/js/` is an IIFE: private by default, publishing a small
API on `window` (`EVER_renderSite`, `EVER_findLayout`, …). No imports, no
exports, no build.

| Module | Responsibility |
|---|---|
| `app.js` | Shared UI: toast, mobile menu, reveal animations, carousel, FAQ accordion, demo modal, "Continue editing", footer year |
| `templates.js` | The v4 engine — layout registry, 27 themes across 10 layouts and 7 occasion types, custom-design CRUD, `EVER_renderSite` / `EVER_renderSiteMini`, state v1→v4 migration, countdowns |
| `mu.js` | Shared layout runtime every layout is built on: header, section titles, vanilla slider (no jQuery), RSVP form, footer, mini-preview scaler |
| `layouts/*.js` | Ten layout modules. Each self-registers its section structure, field specs and `render()` / `mini()` per [LAYOUT-SPEC.md](LAYOUT-SPEC.md) |
| `designer.js` | "Create your own design" modal — name, 5 colours, fonts, ornament, live preview |
| `create.js` | Design-gallery page: cards, filters, "use this design" → checkout |
| `checkout.js` | Order summary, Luhn card validation, → editor |
| `editor.js` | The builder: sidebar generated from each layout's field specs, live preview, reorder/show-hide sections, autosave, publish overlay |

**Load order matters** and is already wired into each page:

```
templates.js  →  mu.js  →  layouts/*.js  →  designer.js  →  app.js  →  <page>.js
```

Layout modules must not render at load time; they only call
`EVER_registerLayout(def)`.

## 4. CSS namespacing

Two design systems coexist in one page and must never bleed into each other:

- **`styles.css`** — the builder chrome (landing page, gallery, checkout, the
  editor's own UI). Owns the global namespace.
- **`css/mu.css`** — the Muhibbi system used by rendered event sites. **Every
  selector is scoped under `.ws`**, applied mechanically by
  `scripts/scope-css.mjs`. It is generated; do not hand-edit it.

The rule: builder chrome never writes a `.ws` selector; layout CSS never writes
an unscoped one. This is what lets the editor render a live event site inside
its own UI without either stylesheet corrupting the other.

## 5. Data model

Everything is in `localStorage`, on the customer's device.

| Key | Shape | Purpose |
|---|---|---|
| `ever-rsvp-event` | `{v:4, layoutId, templateId, nameFont, bodyFont, accent, btnShape, spacing, basics, sections, order}` | The whole event site: content + design |
| `ever-rsvp-selected-design` | template id | What was picked on `create.html` |
| `ever-rsvp-flow` | `"paid"` etc. | Checkout step flag |
| `ever-rsvp-custom-tpl` | `[{id, name, colors, fonts, ornament}]` | User-created designs |

Every `JSON.parse` is wrapped in `try/catch` with a fallback to defaults, so a
corrupt or missing key can never break a page. `templates.js` migrates older
state shapes (v1→v4) on load.

## 6. The user journey

```
index.html ──Get started──► create.html ──pick a design──► checkout.html
                             │            (or "Create          │  pay $25
                             │             your own")          ▼
                             └───────────────► editor.html ◄───┘
                                              edit everything live
                                              autosave → localStorage
```

`index.html`'s "Continue editing" button short-circuits this: if
`ever-rsvp-event` exists it jumps straight to the editor, otherwise it says so
and sends you to the gallery. There is no login because there are no accounts.

## 7. One engine, ten structures

A **layout** is a genuinely different page structure — its own section list,
editor field specs and defaults. All ten are ports of the Muhibbi wedding
template's invitation home pages, re-themeable via five core colours plus a
display font. 27 themes span 7 occasion types across those 10 layouts.

Switching design *within* a layout re-themes instantly. Switching *across*
layouts rebuilds both the page structure and the editor sidebar from the new
layout's field specs, carrying over universal details (names, date, venue,
contacts).

The full contract — `SectionSpec`, `FieldSpec` types, renderer and mini-renderer
rules, the quality bar for adding a layout — is in
[LAYOUT-SPEC.md](LAYOUT-SPEC.md). It is frozen: implement against it rather
than extending it.

## 8. Security posture

**Response headers** live in `config/security-headers.mjs` and are applied by
`next.config.ts` in dev and by the generated `_headers` / `netlify.toml` /
`vercel.json` in production. The CSP confines scripts to self plus inline,
permits fonts only from Google Fonts, permits iframes only from OpenStreetMap,
and sets `frame-ancestors 'none'`.

**Application hardening**, all of it in `public/js/`:

- Every user string is rendered through `esc()` — no raw `innerHTML`
  interpolation of user data anywhere
- `safeUrl()` whitelists schemes on every owner-typed link: only `https:`,
  `http:` and in-page anchors survive, so `javascript:` and `data:` URLs never
  reach an `href` or the map `<iframe>`. Enforced twice — renderer and editor
  field validation
- External links carry `rel="noopener noreferrer"`; the map iframe carries
  `referrerpolicy="no-referrer"`
- Card data is never persisted anywhere — not localStorage, not cookies, not a
  server. Only the order number survives checkout

## 9. Verification

There is no test suite, because there is no build step and no server logic to
test. Verification is:

```bash
bun run check      # eslint (TS shell) + node --check (all 17 browser scripts)
bun run dev        # then exercise the pages in a browser
```

`public/layouts-test.html` renders every layout × theme combination on one page
— the fastest way to eyeball a change across all 27 designs.

| `public/_headers`, `netlify.toml`, `vercel.json` | `scripts/gen-deploy-headers.mjs` | `config/security-headers.mjs` |
