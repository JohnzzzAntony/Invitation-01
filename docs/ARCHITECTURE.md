# Architecture

How Invitara is put together, and why it is put together that way.

Companion documents:
- [LAYOUT-SPEC.md](LAYOUT-SPEC.md) — the frozen v4 contract every layout module implements
- [DEPLOY.md](DEPLOY.md) — going live

---

## 1. The shape of the thing

**The product is `public/`: plain HTML, CSS and vanilla JavaScript.** No
framework, no bundler, no transpile step, no database, no server.

That is a deliberate constraint, not an accident of history. It buys:

- **Deployability** — the deliverable is a folder. Any static host serves it.
- **Longevity** — nothing to upgrade, nothing that rots when a major version lands.
- **Privacy by construction** — with no server there is no place to store customer
  data, so there is none to leak. Everything lives in the customer's browser.

The cost is equally real and worth stating: no accounts, no cross-device sync,
no server-side RSVP aggregation. An event lives in one browser on one device.
The product's copy, its privacy policy and its terms all say so plainly.

Next.js appears in `package.json` for exactly one reason: `next dev` is a
convenient local static server that also applies the production response
headers, so development matches production. **No React code exists in the
product.** `src/app/` is two files that keep the App Router valid.

## 3. The JavaScript modules

Every file in `public/js/` is an IIFE: private by default, publishing a small
API on `window` (`EVER_renderSite`, `EVER_findLayout`, …). No imports, no
exports, no build.

| Module | Responsibility |
|---|---|
| `app.js` | Shared UI: toast, mobile menu, reveal animations, carousel, FAQ accordion, demo modal, "Continue editing", footer year |
| `commerce.js` | **The commerce domain** — plans, feature permissions, theme pricing, the price calculator, projects, the purchase state machine, orders, publish validation and the invitation link. See §11 |
| `templates.js` | The v4 engine — layout registry, 27 themes across 10 layouts and 7 occasion types, custom-design CRUD, `EVER_renderSite` / `EVER_renderSiteMini`, state v1→v4 migration, countdowns |
| `mu.js` | Shared layout runtime every layout is built on: header, section titles, vanilla slider (no jQuery), RSVP form, footer, mini-preview scaler |
| `layouts/*.js` | Ten layout modules. Each self-registers its section structure, field specs and `render()` / `mini()` per [LAYOUT-SPEC.md](LAYOUT-SPEC.md) |
| `designer.js` | "Create your own design" modal — name, 5 colours, fonts, ornament, live preview |
| `create.js` | Marketplace: cards, occasion chips, search, style/price/plan filters, "use this design" → plan choice |
| `picker.js` | Homepage "Pick a design" — six cards painted from theme colours, no layout code (keeps the landing page light) |
| `design.js` | Design detail page and its full-layout live demo |
| `plan.js` | Plan + add-on choice with a live price breakdown |
| `pricing.js` | Plan cards, feature matrix and add-ons, all from commerce.js |
| `dashboard.js` | Project cards, orders, the share sheet |
| `invite.js` | Decodes a published invitation from the URL and wires guest RSVP replies |
| `checkout.js` | Itemised order summary, Luhn card validation, records the order and advances the project to PAID |
| `editor.js` | The builder: sidebar generated from each layout's field specs, live preview, reorder/show-hide sections, autosave, publish overlay |

**Load order matters** and is already wired into each page:

```
templates.js  →  mu.js  →  layouts/*.js  →  commerce.js  →  designer.js  →  app.js  →  <page>.js
```

Layout modules must not render at load time; they only call
`EVER_registerLayout(def)`.

## 4. CSS namespacing

Two design systems coexist in one page and must never bleed into each other:

- **`styles.css`** — the builder chrome (landing page, gallery, checkout, the
  editor's own UI). Owns the global namespace.
- **`css/mu.css`** — the Muhibbi system used by rendered event sites. **Every
  selector is scoped under `.ws`**, applied mechanically by
  `scripts/scope-css.mjs`. It is generated; do not hand-edit it.

The rule: builder chrome never writes a `.ws` selector; layout CSS never writes
an unscoped one. This is what lets the editor render a live event site inside
its own UI without either stylesheet corrupting the other.

## 5. Responsive system

Mobile is the base case; larger screens are progressive enhancement.

### Breakpoints

CSS cannot read a custom property inside `@media`, so the four tiers are
documented constants in `styles.css` `:root` and every query uses them:

| Tier | Query | Range |
|---|---|---|
| Phone | *(base — no query)* | under 640px |
| Tablet | `min-width: 640px` | 640–1023px |
| Laptop | `min-width: 1024px` | 1024–1439px |
| Desktop | `min-width: 1440px` | 1440px and up |

Grids follow one ladder: **1-up → 2-up at tablet → 3-up at laptop**, used by
`.tpl-grid`, `.pick-grid`, `.dash-grid`, `.addon-grid` and `.plan-grid`.

Some `max-width` queries remain from the original desktop-first CSS. They are
phone overrides of older rules, not a second system — new rules use
`min-width`.

### Fluid scale

Between breakpoints, card chrome interpolates with `clamp()` rather than
stepping, so a 360px phone, a 768px tablet and a 1600px monitor each get
sizing that suits them:

| Token | Phone → desktop |
|---|---|
| `--gutter` | 16px → 24px |
| `--card-pad` | 14px → 22px |
| `--card-pad-lg` | 18px → 30px |
| `--card-gap` | 12px → 24px |
| `--card-title` | 17px → 22px |
| `--card-text` | 13px → 14.5px |
| `--card-meta` | 11px → 12.5px |

`.container` is `min(1140px, 100% - 2 × --gutter)`, widening to 1240px at the
desktop tier so a large monitor is not reading a narrow column.

The design thumbnail `.wsm` crops shorter on small screens — `5/4` on a phone,
`4/4.4` on tablet, `4/5` from laptop — because at phone width the card spans
the whole column and a portrait crop would make one card fill the screen.

### Themes

The ten invitation layouts are re-checked at 360 / 768 / 1024 / 1920 after any
CSS change: no horizontal overflow, no clipped text, document width never
exceeding the viewport. Their hero names scale with **container queries**
(`clamp(30px, 8.5cqw, 180px)` in `mu-extra.css`), so they track the width of
the site itself rather than the window — correct both in the editor's narrow
canvas and on a published full-width page.

`css/mu.css` is generated and its media queries come from the vendor template;
responsive corrections belong in `css/mu-extra.css`, which loads after it.

## 6. Data model

Everything is in `localStorage`, on the customer's device.

| Key | Shape | Purpose |
|---|---|---|
| `ever-rsvp-event` | `{v:4, layoutId, templateId, nameFont, bodyFont, accent, btnShape, spacing, basics, sections, order}` | The whole event site: content + design |
| `ever-rsvp-selected-design` | template id | What was picked on `create.html` |
| `ever-rsvp-flow` | `"paid"` etc. | Checkout step flag |
| `ever-rsvp-custom-tpl` | `[{id, name, colors, fonts, ornament}]` | User-created designs |
| `ever-projects` | `[{id, themeId, themeVersion, plan, addons, basePrice, customizationPrice, status, slug, published, orderId, state}]` | One entry per invitation. `state` is the v4 editor state above |
| `ever-orders` | `[{id, number, projectId, themeId, plan, addons, themePrice, planPrice, customization, subtotal, discount, vat, total, status, paidAt}]` | Paid orders. Amounts only — **never card data** |
| `ever-active-project` | project id | Which invitation the editor is currently on |

Every `JSON.parse` is wrapped in `try/catch` with a fallback to defaults, so a
corrupt or missing key can never break a page. `templates.js` migrates older
state shapes (v1→v4) on load.

`ever-rsvp-event` remains the editor's working key: opening a project mirrors
its `state` into it, and autosave mirrors it back. That is what let the whole
commerce layer be added without touching how `editor.js` reads or writes
content.

## 7. The user journey

```
index.html ──Pick a design──► create.html ──► design.html ──Use this design──┐
   (or the homepage picker)    marketplace     detail page                   │
                                                                             ▼
                                                                       plan.html
                                                                    Basic/Pro/Advanced
                                                                       + extras
                                                                             │
                              dashboard.html ◄── checkout.html ◄── editor.html
                              projects, orders     itemised,        customise,
                              share sheet          records order    validate, publish
                                     │
                                     ▼
                              invite.html  ← the link a guest opens
```

"Continue editing" short-circuits this: one saved invitation opens straight in
the editor, several open the dashboard, none sends you to the marketplace with
an explanation. There is no login because there are no accounts.

## 8. One engine, ten structures

A **layout** is a genuinely different page structure — its own section list,
editor field specs and defaults. All ten are ports of the Muhibbi wedding
template's invitation home pages, re-themeable via five core colours plus a
display font. 27 themes span 7 occasion types across those 10 layouts.

Switching design *within* a layout re-themes instantly. Switching *across*
layouts rebuilds both the page structure and the editor sidebar from the new
layout's field specs, carrying over universal details (names, date, venue,
contacts).

The full contract — `SectionSpec`, `FieldSpec` types, renderer and mini-renderer
rules, the quality bar for adding a layout — is in
[LAYOUT-SPEC.md](LAYOUT-SPEC.md). It is frozen: implement against it rather
than extending it.

## 9. Commerce: plans, pricing and projects

All of it lives in `public/js/commerce.js`, published as `window.EVER_C`.
`templates.js` stays a pure rendering engine — no price or plan concept leaks
into it. The two are joined by theme id through `EVER_C.themeCommerce(id)`.

**Plans.** Three: Basic (AED 29), Pro (59), Advanced (99). Each carries a list
of permission ids and inherits everything below it, so `can(plan, perm)` is the
single question the rest of the app asks.

**Theme pricing.** A per-layout tier gives each design its base price, its
editor ceiling and which plans it supports. A design's *features* are derived
from its layout's own section list, so a theme can never advertise a section
its layout does not render.

**Price.** One function, `EVER_C.quote({themeId, plan, addons, discount})`,
returns the itemised breakdown:

```
design base + plan + optional add-ons − discount + 5% VAT = total
```

Every screen that shows a price — design card, detail page, plan picker,
checkout, billing — calls it. Two screens cannot disagree.

**One design per invitation (§3).** `createProject(themeId)` permanently binds
a project to one theme. Once paid, the editor replaces its theme picker with an
explanation and a link to start another invitation; it never silently swaps
what was bought.

**State machine.** `DRAFT → DESIGN_SELECTED → PLAN_SELECTED → CUSTOMIZING →
READY_FOR_PAYMENT → PAYMENT_PENDING → PAID → READY_TO_PUBLISH → PUBLISHED →
ARCHIVED`, with `PAYMENT_FAILED → RETRY_PAYMENT`. `setStatus()` refuses any
transition the machine does not allow.

**Feature gating.** `editor.js` builds its sidebar from layout field specs, so
gating is applied in one place — `applyLocks()` — after the sidebar renders.
Locked controls stay visible but disabled and carry a `🔒 Available in Pro`
prompt, because a customer should be able to see what a higher plan buys.

> **Scope limit — frontend only.** The spec (§35) requires the backend to
> enforce permissions too. This build has no backend, so the gating is
> advisory: it shapes the UI but cannot stop a determined user editing
> `localStorage`. Nothing of value is protected by it — the invitation is the
> customer's own content on their own device — but it is not a security
> boundary and must not be treated as one. Adding a server means moving
> `quote()` and `can()` behind an API and re-checking both on write.

## 10. Publishing and sharing

There is no server, so a published invitation travels **inside its own URL**:
`publish()` assigns a slug, then `inviteUrl()` base64-encodes the invitation
state into the link's hash. `invite.html` decodes it and renders the real
layout.

That is what makes a shared link genuinely open on a guest's phone with no
account and no database — verified with `localStorage` completely empty. The
cost is a long URL (~6 KB), which rules out a QR code (QR tops out near
2.9 KB). A QR encoding a link that only worked on the host's own device would
be worse than none, so it is deliberately not offered.

Guest RSVP replies have nowhere to POST. `invite.js` composes the reply into a
WhatsApp or e-mail message addressed to the host using the contact details the
host entered — one tap for the guest, and the host receives it. Aggregated RSVP
counts in a dashboard need a backend and are not in this build.

## 11. Security posture

**Response headers** live in `config/security-headers.mjs` and are applied by
`next.config.ts` in dev and by the generated `_headers` / `netlify.toml` /
`vercel.json` in production. The CSP confines scripts to self plus inline,
permits fonts only from Google Fonts, permits iframes only from OpenStreetMap,
and sets `frame-ancestors 'none'`.

**Application hardening**, all of it in `public/js/`:

- Every user string is rendered through `esc()` — no raw `innerHTML`
  interpolation of user data anywhere
- `safeUrl()` whitelists schemes on every owner-typed link: only `https:`,
  `http:` and in-page anchors survive, so `javascript:` and `data:` URLs never
  reach an `href` or the map `<iframe>`. Enforced twice — renderer and editor
  field validation
- External links carry `rel="noopener noreferrer"`; the map iframe carries
  `referrerpolicy="no-referrer"`
- Card data is never persisted anywhere — not localStorage, not cookies, not a
  server. Only the order number survives checkout

## 12. Verification

There is no test suite, because there is no build step and no server logic to
test. Verification is:

```bash
bun run check      # eslint (TS shell) + node --check (all 17 browser scripts)
bun run dev        # then exercise the pages in a browser
```

`public/layouts-test.html` renders every layout × theme combination on one page
— the fastest way to eyeball a change across all 27 designs.
